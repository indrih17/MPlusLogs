# Companion: аудит квоты WCL и границы защиты

Дата: 18 октября 2026. Аудит кода и сохранённых ответов, без новых запросов к WCL API. Внешняя конфигурация, учётные данные и публикация не изменялись.

## Вывод для владельца

Локальный часовой бюджет и разовый предел полезны: они сдерживают случайную нагрузку, ошибочный импорт и обычное использование программы. Они **не защищают общий OAuth client от намеренного злоупотребления владельцем изменённой программы**. Публичный Client ID не является секретом; PKCE не подтверждает неизменность исполняемого файла. Пользователь с собственной разрешённой WCL-сессией может выполнять разрешённые для неё запросы вне Companion. Для такого злоупотребления не требуется красть чужой токен.

В штатном интерфейсе запрос 1000 персонажей уже отклоняется до загрузки: `process_request` ограничивает batch 250, single 20; GUI задаёт 120 локальных обращений/час для shared client и 3600 для personal. Однако 120 — это лимит обращений конкретного локального состояния, а не глобальная доля общей квоты и не 120 WCL points. Несколько установок/пользователей вместе могут исчерпать общую квоту даже без нарушения этих ограничений. Удаление/разделение локальной базы, изменение клиента и прямой доступ к API обходят локальные проверки.

Не вводился новый произвольный разовый предел. Целесообразно сохранить существующие ограничения, кэш, cooldown и остановку по квоте, дополнив их резервированием стоимости параллельной работы. Для настоящего общего барьера нужен enforcement на стороне WCL либо доверенного сервера, через который проходят **все** обращения к защищаемой квоте. Личный client уменьшает зависимость пользователя от общего client.

## Что подтверждено источниками

1. [Официальная документация OAuth WCL](https://www.warcraftlogs.com/api/docs) описывает client credentials, authorization code и PKCE для приложений, которые не могут хранить client secret. User endpoint принимает пользовательские Bearer-токены. Из документации не следует привязка токена к конкретному неизменённому Companion. PKCE защищает получение токена от перехвата кода; это не механизм нормирования расходов.
2. [RateLimitData](https://www.warcraftlogs.com/v2-api-docs/warcraft/ratelimitdata.doc.html) содержит `limitPerHour`, `pointsSpentThisHour`, `pointsResetIn`, `currentRequest: JSON!`. Первые поля описывают часовую квоту API key. У JSON не документированы внутренние поля, момент снимка и порядок финального списания относительно ответа. Отдельных типизированных полей квоты user points в опубликованном объекте нет. Не следует придумывать такие поля или считать дельту параллельных снимков стоимостью одного запроса.
3. [Директива onlySpendUserPoints](https://www.warcraftlogs.com/v2-api-docs/warcraft/onlyspenduserpoints.doc.html) имеет форму `query @onlySpendUserPoints(enabled: true) { ... }`. Без OAuth user или при поле, которое потребовало бы non-user points, WCL возвращает ошибку. Даже с директивой в начале запроса ставится hold **1 app point**; при успехе/nonfatal error он освобождается. Хотя бы один app point должен быть доступен. Для fatal error освобождение источником не обещано.
4. [Схема Character](https://www.warcraftlogs.com/v2-api-docs/warcraft/character.doc.html) описывает `zoneRankings`/`encounterRankings` и user endpoint для приватных логов, но не гарантирует оплату нужных Companion полей через user points. Наличие пользовательского OAuth само по себе не доказывает такую возможность.

Ограничение проверки: прямое открытие WCL документации получило HTTP 403; исследователь проверил индексированные копии официальных страниц, обход от предыдущего дня до двух недель. Неподтверждённые настройки аккаунта и поведение живого API не выдаются за проверенный факт.

## Реальная граница доверия

| Участник / ситуация | Что ограничивает штатный код | Что остаётся возможным |
|---|---|---|
| Обычный импорт слишком большого списка | Проверка размера до обработки, `max_fetch`, часовой счётчик | Суммарная разрешённая нагрузка многих установок |
| Многократный refresh одного персонажа | Кэш/TTL, отрицательный кэш, cooldown 300 секунд; неудачная попытка тоже считается | Другие персонажи; отдельное локальное состояние |
| Параллельная загрузка без свежих ответов | Атомарное SQLite-резервирование попыток и теперь points; upstream reserve | Уже отправленные запросы не отозвать; неизвестная будущая стоимость может быть выше оценки |
| Пользователь изменённого клиента | WCL проверяет его действительную авторизацию и серверные лимиты | Обход SQLite/часового/разового лимита и формы GraphQL в рамках разрешений сессии |
| Отсутствующая авторизация | OAuth и проверки WCL | Один Client ID не даёт готового пользовательского токена; обещать анонимный доступ нельзя |
| Исчерпание общей квоты другим участником | Локальная остановка после наблюдения низкого остатка/429 | Локальный клиент не может запретить чужие обращения или восстановить общую квоту |

Пути проверки: `wcl_oauth.Session`/`login`/`validate_access`, `personal_api.budget_path`, `companion_gui.App` при создании `bridge.Client`, `clipboard_companion.Client._query`/`process_request`, `build_database` и `api_budget.Budget`. Секреты и настройки при аудите не печатались. Локальная база разделена по client, но это организационная изоляция штатного клиента, а не серверная выдача персональной квоты.

## Почему 501 и 338,64 не являются итоговым счётом

Повторно прочитаны только числовые поля 50 сохранённых raw-ответов по ключам из локального measurement:

| Метрика сохранённого прогона | Значение |
|---|---:|
| Ответов / профилей | 50 / 50 |
| Сумма `currentRequest.total` | 501,00 |
| Стоимость каждого из 50 ответов | 10,02 |
| Первый `pointsSpentThisHour` | 1 |
| Максимальный `pointsSpentThisHour` | 338,64 |
| `limitPerHour` | 3600 |
| `pointsResetIn` | 3597–3600 секунд |
| Измеренная длительность | 3,606 секунды |

Это измерения одного запуска, не новый сетевой эксперимент. Локальные исходники: `.diagnostic-local/preview-50-measurement.json`, `preview-50-summary.json`, `preview-50-report.md`; raw-кэш остаётся в пользовательском каталоге и не включается в публикацию.

Предварительный hold и отсутствие документированного момента снимка допускают, что снимки не включали финальный расход всех параллельных запросов. Это **объяснение, согласующееся с документацией**, а не доказанный полный порядок внутреннего биллинга WCL. Максимум 338,64 не является подтверждённым окончательным расходом; 501 — сумма возвращённых затрат запросов, но без документированной семантики JSON её нельзя объявлять доказанным финальным списанием именно app points. Нельзя выводить из этого «параллельность сэкономила 162,36 points».

Один максимум снимков защищает от восстановления остатка из ответов, пришедших не по порядку, но не резервирует ещё не отражённую стоимость отправленной работы. Завершение клиентского HTTP-запроса также не доказывает, что в его снимке отражены все списания группы.

## Реализованное локальное улучшение

Первоначальный аудит изменял выделенный `tools/api_budget.py`. После пользовательского воспроизведения ложного запрета учёт исправлен также в `clipboard_companion.py` и обработке отложенных ошибок кэша `build_database.py`. Старые таблицы SQLite, история обращений, часовой лимит и cooldown сохранены.

Первоначальная модель повторно резервировала все обращения за час и оказалась неверной. В реальном состоянии WCL сообщил 502/3600, но 164 исторических обращения умножились на ошибочно выведенную из общей дельты цену 163,36. Получился резерв 26 791,04 и ложная блокировка. Новая модель хранит историю и денежные резервы раздельно:

```text
C = max(1, максимальная явно полученная стоимость currentRequest.total)
localReservedPoints = сумма отдельных pending/uncertain резервов
localCompletedFloor = исходный расход окна + сумма завершённых локальных затрат
projectedSpentThisHour = max(max_observed_spent_in_window, localCompletedFloor) + localReservedPoints
reserve = max(100, 0.10 * limitPerHour)
следующая попытка допускается, если limit - projected - C >= reserve
```

Атомарный `reserve()` до отправки возвращает идентификатор допуска вместе с прежним числовым временем ожидания. После ответа `complete()` снимает pending и фиксирует фактическую стоимость. Более высокая измеренная цена может уточнить только незавершённые резервы; завершённая работа сохраняет свою цену. Снимок без `currentRequest.total` никогда не становится ценой одного запроса. Отмена до отправки снимает денежный резерв, сохраняя историю; timeout после отправки с неизвестной стоимостью остаётся uncertain. У ошибки с известной стоимостью резерв завершается так же, как у успешного ответа. Перезапуск сохраняет ledger.

Уже допущенный запрос проверяется повторно только на реальный upstream stop, а не на свой собственный локальный резерв. При миграции старые attempts не превращаются в pending и прежняя дельта не переносится в цену запроса. Кэшированная ошибка квоты перепроверяется: после восстановления доступного бюджета старое ожидание не блокирует повторную загрузку; настоящее 429 по-прежнему соблюдается.

Для сохранённой группы 50 × 10,02 локальная нижняя граница равна 501; последующий снимок WCL 501 не превращает её в 1002. Это инженерная оценка допуска, а не доказанный финальный биллинг: неизвестные цены, внешняя нагрузка и момент снимка остаются ограничениями. Запас квоты и настоящий upstream stop сохраняются. После истечения upstream-окна новый ответ обновляет исходное окно учёта.

Добавлены поля `snapshot()`:

- `projectedSpentThisHour`: расход для локального admission control, не для отображения как «потрачено WCL»;
- `localReservedPoints`: дополнительный консервативный локальный резерв;
- `requestCostEstimate`: положительная текущая оценка C.

Прежнее `pointsSpentThisHour` по-прежнему означает наблюдаемый upstream high-water mark. Не подменять им финальный биллинг и не менять его семантику ради обратной совместимости.

### Интеграция с адаптивными волнами

Для `Client.parallel_capacity(remaining_profiles)` использовать `snapshot.get('projectedSpentThisHour', snapshot['pointsSpentThisHour'])` при расчёте доступных points. Уже существующий `Budget.reserve()` остаётся окончательной атомарной локальной проверкой; одна оценка размера волны не предотвращает гонку между несколькими вызовами. Ключи `requestCostEstimate`/`localReservedPoints` доступны для объяснения остановки и диагностики, но это не фактический расход API. При неизвестной цене сохранять probe/адаптацию; не выводить цену одного профиля из разницы двух параллельных снимков.

После завершения двух параллельных задач координатор выполнил эту интеграцию: размер волны учитывает `projectedSpentThisHour`, а стоимость обращения берётся не ниже `requestCostEstimate`. Отдельный интеграционный тест проверяет уменьшение допустимой волны с 2 до 1 и затем до 0 после резервирования обращений, когда новые ответы ещё не пришли.

`build_database.py`, `clipboard_companion.py`, `test_parallel_profiles.py`, GUI, OAuth, `wcl_sync.py` и `personal_api.py` в рамках этого аудита не редактировались. Часовые лимиты 120/3600 и batch 250/single 20 не менялись.

## Варианты настоящей защиты общего лимита

| Вариант | Реальная гарантия / граница | Что требуется решить |
|---|---|---|
| Личный OAuth client | Запросы идут от личного client, а не общего MPlusLogs. Документированная квота API key поддерживает такую изоляцию; независимость всех возможных user/account лимитов не доказана | UX уже существует; владельцу решить, делать ли personal основным режимом |
| `onlySpendUserPoints` в штатных запросах | WCL применяет директиву к содержащему её запросу; клиент не может заставить такой запрос оплачивать запрещённое поле app points | Проверить нужные поля по документации/с WCL либо в отдельно разрешённом эксперименте. Клиент может убрать директиву; общий app client не становится защищённым от этого, holds остаются |
| Настройки WCL, если доступны | Только серверная обязательная политика client-wide могла бы ограничить прямые запросы независимо от программы | В просмотренных источниках не найдены обязательные per-user budgets для client, app-wide force-user-points, allowlist persisted queries или attestation. Уточнить у WCL; отсутствие в найденной документации не доказывает отсутствия функции |
| Доверенный серверный посредник | Сервер хранит свой credential, принимает только разрешённые прикладные операции, проверяет пользователей и атомарно ограничивает общие/персональные points и concurrency | Серверный кэш, антиабьюз/много аккаунтов, доступность и затраты. Не выдавать пользователю credential/token для прямого расходования защищённого резерва |

Посредник не защищает квоту, пока сохраняется публичный прямой путь к тому же резерву. Для гарантии надо закрыть этот путь средствами WCL либо выделить посреднику отдельный действительно закрытый client/credential. Нельзя положить client secret в распространяемый Companion и считать его серверным секретом. Redirect URI и PKCE не заменяют этот барьер для владельца легитимной сессии.

Сервер не создавался, внешние настройки не менялись, user-points директива без проверки совместимости не включалась. Решения владельца: желаемый режим shared/personal; приемлемая консервативность локального резерва; запрос к WCL о серверных политиках; необходимость отдельного серверного продукта. Локальная доработка не требует этих решений, чтобы работать в существующем клиенте.
