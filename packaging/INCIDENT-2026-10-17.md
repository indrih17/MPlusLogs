Отказы затрагивали импорт ответов с повторяющимися рейтингами специализации.
Сохранённые профили не удалялись. В групповом ответе один такой профиль

Число затронутых пользователей и точный момент первого отказа неизвестны.

## Конкретный триггер

При первоначальной диагностике в сохранённом ответе для одного персонажа
нашлись две строки рейтинга Holy: 3637 и 4239. В исходном кэше WCL обе строки
находились уже внутри каждого массива allStars, а не возникали при объединении
двух кандидатов или массивов damage и healing. В обеих был partition=1.

Сокращённый пример входа (имя и остальные данные не нужны для воспроизведения):

```json
{
  "allStars": [
    {"spec": "Holy", "rank": 3637, "partition": 1},
    {"spec": "Holy", "rank": 4239, "partition": 1}
  ]
}
```

Companion экспортировал это как две строки внутри одного профиля:

```text
R<TAB>Holy<TAB>3637
R<TAB>Holy<TAB>4239
```

Причина, по которой WCL вернул два места, не установлена. Это не доказательство
двух паладинов в группе, разных partition или ошибки на стороне WCL.
Нельзя достоверно выбрать правильное место только по этим данным.
Файл last-result.mpl перезаписывается при следующих запросах; текущий файл уже
содержит другой успешный ответ и не является неизменяемым артефактом инцидента.
В тестах сохранён минимальный синтетический пример исходной структуры.

## Цепочка отказа

1. При добавлении рейтингов специализаций normalizer в tools/wcl_sync.py
   начал переносить каждую допустимую строку allStars в specRanks без объединения.
2. Новый обработчик R в Data.lua одновременно потребовал уникальности spec:
   `if entry.spec==spec then error(...) end`.
3. На второй строке Holy срабатывала ошибка «Некорректная запись профиля».
   Значение rank даже не требовалось сравнивать: одинаковый повтор тоже падал.
4. MPL.Parse выполнял разбор всего ответа под одним pcall и возвращал nil.
   MPL.Import / MPL.ReceiveReply не доходили до MPL.StoreProfiles.
5. В пакетном запросе по той же причине не сохранялись и корректные соседи.

Корневая причина — неподтверждённое предположение об уникальности внешних
данных и несовместимые требования производителя и потребителя одного формата.
Усилитель — необязательное дополнительное поле могло сорвать основной сценарий.
Это наша ошибка проектирования и проверки границы, а не ошибка пользователя.

## Почему проверки пропустили баг

- Сквозной тест Python → текст ответа → Lua → UI уже существовал, но его
  fixture содержал только уникальные специализации Assassination и Outlaw.
- Тест не только не проверял допустимость повторов: он явно требовал отказа
  на двух строках Outlaw с разными местами, закрепляя ошибочное предположение.
- Наличие сотен зелёных тестов подтверждало соответствие этому предположению,
  но не его правильность для реальных ответов WCL.
- Сборка и smoke-проверка установщика проверяют другие классы отказов
  (запуск, ресурсы, упаковку), поэтому сами по себе такой баг не обнаруживают.

## Уже сделано

В опубликованном исправлении одинаковые повторы объединяются, противоречивое
место скрывается; сами логи загружаются. Обе стороны исправлены независимо:
новый аддон принимает ответы старого Companion, новый Companion не отправляет
противоречивые рейтинги старому аддону. Проверки структуры, идентичности,
сезона и лимитов ответа сохранены.

При разборе дополнительно добавлены два сквозных теста в test_spec_details.py:
48 сценариев без сети и без личного кэша. Проверяются отсутствие рейтингов,
одно место, одинаковые повторы, конфликт, третий повтор после конфликта и
обратный порядок; одиночный и групповой запросы; DPS и HPS; нормализованные
и старые ненормализованные ответы. Проверяются число импортов, сохранность
обоих подземелий и соседнего кандидата, метрика и итоговые рейтинги.
Эти тесты подхватываются существующей командой unittest discover в публикации
и GitHub Actions. Они не меняют содержимое сборок аддона и Companion.

Проверка на неизменённом историческом коде, загруженном из Git в отдельный
тестовый runtime, дала для 24 сценариев полного обмена:

## Следующие меры, по приоритету

1. Для каждого изменения формата проверять основной пользовательский результат:
   «валидные логи импортируются», а не только новую иконку или отсутствие crash.
   Добавлять обезличенный пример реальной структуры и отрицательные случаи
   на границе Companion → аддон; проверять оба порядка обновления компонентов.
2. Определять политику каждого дополнительного поля: одинаковые значения
   объединить, неоднозначные скрыть, отсутствие показать как отсутствие.
   Структурные ошибки и несовпадение персонажа не проглатывать. Не превращать
   любое исключение в «публичных логов нет» и не кэшировать его как отсутствие.
3. Отдельно спроектировать изоляцию ошибок кандидатов. Сейчас повреждённая
   обязательная запись по-прежнему отклоняет весь пакет. Безопасный следующий
   шаг — проверять профиль до упаковки и возвращать F для конкретного кандидата;
   проверка целостности конверта и списка кандидатов должна остаться строгой.
   Это предложение, а не уже реализованная защита от любых ошибок пакета.
4. Перед публикацией изменений протокола проводить короткую проверку в WoW:
   одиночный профиль, группа, хил/DPS, существующий кэш и прежний Companion.
   Автотесты используют Lua с имитацией API WoW и не заменяют проверку клиента.
5. Для изменений протокола рассмотреть отдельный preview-канал с ручной
   проверкой до переключения общего автообновления. Сейчас публикация сразу
   обновляет общий канал; поэтапный rollout ещё не реализован.

Сохранение необязательной функциональности не должно стоить потери основной.
Полностью исключить будущие баги нельзя; эти меры адресуют конкретные
предположения, пропущенный сценарий и масштаб отказа данного инцидента.
